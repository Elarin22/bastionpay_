## 로그인 실패가 Wazuh에서 보이지 않은 문제

- 문제점. 앱과 Graylog에는 로그인 실패 이벤트가 있었고 Wazuh Agent는 연결 상태였지만 Dashboard에 기대한 경보가 없었다.
- 원인 확인. 파일 경로와 그룹 설정을 점검한 뒤 `wazuh-logtest`에 실제 JSON을 입력했다. JSON은 해석됐고 처음에는 일반 룰 1002가 선택됐다. 분석 룰 매칭을 별도로 확인할 수 있었다. 서버 이전 후에는 달라진 실행 폴더가 수집 대상과 일치하는지도 점검했다.
- 해결. 수집 경로를 새 앱 위치에 맞추고 룰 설정을 검사했다. 테스트 이벤트에서 대상 룰이 선택되는지 먼저 보고 실제 앱 실패 요청으로 대시보드와 n8n을 다시 확인했다.
- 결과. 11월 5일 기록에서 S1 실패 5건과 Wazuh 룰 100268, 티켓 #29 생성, Graylog 경유 갱신을 확인했다. 같은 시험에서 자동 차단이 의도보다 넓은 조건에 적용되는 문제도 관찰했다.

## 발표 피드백과 보완

- 문제점. 발표에서 VLAN 구간과 구성을 보여줬지만 WEB20과 DB30이 실제로 통신하는 과정이 빠졌다.
- 원인. 구성 요소 이름과 결과 위주로 설명해, TAP과 브리지, pfSense 라우팅과 규칙 평가가 요청 하나에 어떻게 이어지는지 연결하지 않았다.
- 해결. [VLAN 설명](VLAN.md)과 개인 포트폴리오에 TCP 3306 요청 경로를 넣었다. TEST60에서 DB30 TCP 8080을 기본 차단하고 임시 허용한 뒤 다시 차단한 팀 캡처를 연결했다.
- 결과. 어떤 목적지와 포트를 시험했고, 왜 응답하거나 차단됐는지 로그와 함께 설명할 수 있다. 관제 이전 뒤의 학원망 경로, 미연결 SOAR50, SOC40 규칙의 이전 목적지도 명시했다.

다음에는 관제 서비스 이전 뒤 VLAN별로 실제 수신까지 다시 측정하고, 두 수집 경로의 지연과 중복 티켓을 기록하겠다. 현재 저장소의 K6-B `TIER_CHANGED`에는 회원 등급 변화와 ADMIN 역할 변화의 의미 차이가 있다. 별도의 역할 변경 이벤트에 변경 전후 role과 대상 ID를 기록하고 검증한 뒤 권한 회수·잠금을 연결하는 편이 안전하다. 발표를 준비하면서 서비스가 켜졌다는 화면보다 요청, 원본 이벤트, 경보, 대응 이력을 한 사건으로 연결하는 기록이 중요하다는 점을 배웠다.
